# 사후 검증 규약

사후 검증은 판정 방법이 성공과 부진을 **결과를 모른 채** 가려낼 수 있는지 시험한다. 결과가 새어 들어가면 판정은 좋아 보이기만 하고 아무것도 증명하지 못한다. 그래서 이 규약의 거의 모든 규칙은 "누가 언제 무엇을 볼 수 있는가"에 관한 것이다.

## 1. 사례 선정

- **한 쌍으로 고른다.** 원작 규모와 편성이 비슷한데 결과가 엇갈린 두 작품. 결과가 좋았던 작품만 보면 판정이 좋아 보이는 쪽으로 기운다.
- **결정 시점은 확인된 날짜로 잡는다.** 판권 계약일을 알면 그날, 모르면 확인된 가장 이른 공식 발표일(예: 출연진 발표) 전날을 컷오프로 쓰고, 근거를 `key.json`의 `cutoff_basis`에 적는다.
- **지난 결정을 평가하지 않는다.** 부진 사례를 넣는 목적은 판정 방법을 시험하는 것이다. 해당 사업부와 함께 고르고, 결과는 판정 방법을 고치는 데만 쓴다.
- 선정은 사람이 한다. 오케스트레이터는 후보만 제시한다.

## 2. 폴더와 접근 권한

```
_workspace/backtest/{pair}/          # pair는 중립 코드(예: bt-2026q4-1). 작품명을 넣지 않는다
├── sealed/                          # 큐레이터·성과 분석가·오케스트레이터만
│   ├── key.json                     # 사례 코드 ↔ 실명, 컷오프, 가린 용어
│   ├── case-{X}_sources.md          # 실명 출처 대응표
│   └── 40_analyst_outcomes.md       # 실제 결과(잠금 뒤에만)
├── blind/case-{X}/                  # 판정단은 여기만 읽는다
│   ├── 10_curator_dossier.md
│   ├── 20_panel_format.md · 21_panel_global.md · 22_panel_rights.md
│   └── 30_panel_verdict.md
├── blindcheck_{X}_{단계}.txt        # 누출 검사 기록
├── lock.sha                         # 블라인드 판정 잠금 해시
└── 41_analyst_hit-table.md          # 적중표
```

`key.json` 형식:

```json
{
  "pair": "bt-2026q4-1",
  "leak_words": ["시청률", "종영", "최종회", "흥행", "참패", "부진", "역주행"],
  "cases": {
    "A": { "title": "실제 작품명", "aliases": ["약칭", "영문 제목"],
           "terms": ["작가명", "주인공 이름", "제작사", "방송사", "주연 배우"],
           "cutoff": "2026-06-09", "cutoff_basis": "출연진 발표(2026-06-10) 전날", "slug": "real-slug" },
    "B": { "...": "..." }
  }
}
```

## 3. 가림 규칙(큐레이터)

| 가릴 것 | 바꾸는 법 |
| --- | --- |
| 작품명·약칭·영문 제목 | 작품 A / 작품 B |
| 작가·발행사·제작사·방송사·배우 | 작가 X, 제작사 Y 같은 역할 표기 |
| 캐릭터 이름 | 주인공 갑, 상대역 을 |
| 고유한 설정어·유명 대사·수상명 | 일반 설명으로 바꾼다(예: "회사형 괴담 생존물") |
| 정확한 수치 | 판정에 필요한 정밀도만 남긴다(예: "누적 조회 1억 회대") |

남길 것: 장르, 형식, 연재 기간의 길이, 규모의 자릿수, 성장 속도, 서사 구조, 결정 시점까지의 확장 이력. 판정에 필요한 정보까지 지우면 판정 방법이 아니라 정보 부족을 시험하게 된다.

## 4. 누출 검사

```bash
python3 .claude/skills/backtest-protocol/scripts/blind_check.py \
  --key _workspace/backtest/{pair}/sealed/key.json --case {X} \
  _workspace/backtest/{pair}/blind/case-{X}/ > _workspace/backtest/{pair}/blindcheck_{X}_{단계}.txt
```

| 종료 코드 | 뜻 | 조치 |
| --- | --- | --- |
| 0 | 깨끗함 | 다음 단계 |
| 1 | 누출(가린 용어·컷오프 이후 날짜) | 큐레이터가 고친다. 판정 뒤에 나왔다면 그 판정은 버리고 다시 한다 |
| 2 | 판정단이 작품을 알아봄 | 판정은 잠그되 적중표에 "오염 가능"으로 따로 표시한다 |

`WARN`(결과를 암시하는 단어)은 큐레이터가 줄마다 확인해 필요하면 고친다. 단어가 있어도 결정 시점 이전 맥락이면 남겨도 된다.

검사는 세 번 한다: 자료를 만든 뒤(`dossier`), 렌즈 분석 뒤(`analysis`), 최종 판정 뒤(`verdict`).

## 5. 블라인드 판정 규칙(판정단)

- 블라인드 폴더와 스킬 파일만 읽는다. `_workspace/ips/`, `sealed/`, `ledger/`, `deliverables/`는 열지 않는다.
- 웹·셸 도구를 쓰지 않는다. 기억으로 작품을 짐작하게 되더라도 그 짐작을 근거로 쓰지 않는다.
- 렌즈별 방법은 실제 진단과 같다: format → `format-expansion`, global → `global-fit`, rights → `rights-revenue-check`, judge → `ip-investment-review`(「7. 블라인드 판정」).
- 자료에 없는 사실을 만들지 않는다. 근거가 없는 포맷은 "판단 보류"다.
- 최종 판정 끝에 `## 인식 점검`을 둔다: 알아본 것 같은가(예/아니오/모름), 짐작한 작품명, 짐작이 판정에 영향을 줬는가.

## 6. 잠금과 결과 공개 순서

1. 두 사례의 `30_panel_verdict.md`가 모두 나오고 `verdict` 누출 검사가 끝난다.
2. 오케스트레이터가 잠근다: `shasum _workspace/backtest/{pair}/blind/case-*/30_panel_verdict.md > _workspace/backtest/{pair}/lock.sha`
3. 블라인드 판정을 판정 원장에 기록한다(`ledger.py add-verdict`, `mode: backtest`).
4. **그 뒤에야** 성과 분석가가 실제 결과를 모은다. 결과를 모으기 전에 `shasum -c lock.sha`로 판정이 바뀌지 않았는지 확인한다.

순서가 바뀌면(결과를 먼저 보고 판정을 고치면) 그 사후 검증은 무효다. 무효가 되면 숨기지 말고 보고한다.

## 7. 오염 판정

| 상황 | 처리 |
| --- | --- |
| 판정단이 작품명을 맞힘(종료 코드 2) | 적중표에 "오염 가능", 적중률을 오염 사례 포함·제외로 둘 다 보인다 |
| 판정 뒤 누출 발견 | 판정 폐기, 자료를 고쳐 다시 판정, 폐기 사실을 기록 |
| 컷오프 이전 자료가 너무 적음 | 진행하지 않고 다른 사례를 사람에게 요청 |

AI가 학습한 지식에 실제 결과가 들어 있을 수 있다는 한계는 가림으로 줄일 뿐 없앨 수 없다. 적중표 한계 칸에 항상 적는다.
