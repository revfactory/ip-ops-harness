# 성과 분석과 판단 기준 수정

제안서 설계 원칙 3번은 "성과가 다음 판단으로 돌아온다"다. 판정을 날짜와 함께 남기고, 결과가 나오면 대조해 판단 기준을 고친다. 이 스킬의 목표는 **판정 방법의 어느 부분이 왜 맞거나 틀렸는지** 찾는 것이다. 몇 개 사례로 규칙을 크게 바꾸는 것도, 틀린 판정을 운으로 넘기는 것도 경계한다.

## 1. 실제 결과 기록

- 사후 검증에서는 `lock.sha`가 확인된 뒤에만 결과를 모은다: `shasum -c _workspace/backtest/{pair}/lock.sha`
- 포맷마다 성공·부진·미정을 정하고 근거를 남긴다. 기준은 결과를 보기 전에 정한다.

| 포맷 | 성공 판단 근거(예) | 부진 판단 근거(예) |
| --- | --- | --- |
| 드라마 | 동시간대·채널 평균 대비 시청률, OTT 공식 순위 진입, 원작 역유입 | 채널 평균 미달, 조기 종영, 순위 미진입 |
| 웹툰(노블코믹스) | 플랫폼 랭킹, 원작 거래액 반등 | 랭킹 하위, 연재 중단 |
| 공연·전시 | 예매율·매진, 재관람률 | 할인 판매 확대, 조기 폐막 |
| 해외 정식판 | 국가별 열람 순위 유지, 유료 전환 | 순위 이탈 |

- 결과마다 `ledger.py add-outcome --ip {실제 슬러그} --format {판정의 포맷 이름 그대로} --date ... --result ... --evidence "..." --url ...`로 기록한다. 포맷 이름을 판정과 다르게 쓰면 대조가 빠진다.
- 출처 등급은 `ent-research` 기준을 따른다. 시청률은 집계 기관·지역을 적는다.

## 2. 적중표

`ledger.py hits --mode backtest --pair {pair}`로 계산한다. 손으로 세지 않는다.

- **포맷별 적중**: A·B는 '추진', C·D는 '보류'로 보고 실제 결과와 맞춘다. 실행되지 않은 포맷, 결과가 미정인 포맷은 평가하지 않고 그 수를 적는다.
- **쌍 구분**: 같은 포맷에서 성공 사례의 판정이 부진 사례보다 높으면 "구분 성공", 같으면 "동점", 반대면 "역판정". 쌍 구분이 포맷별 적중보다 중요하다. 판정 방법이 둘을 가려낼 수 있는지가 이 검증의 질문이기 때문이다.
- **오염**: 판정단이 작품을 알아본 사례는 "오염 가능"으로 표시하고 적중을 포함·제외 두 가지로 보인다.
- **사람 결정**: 실제 진단에서 사람 결정이 기록돼 있으면 사람 적중도 함께 보인다. AI와 사람 가운데 누가 맞았는지가 아니라, 어긋난 칸에서 무엇을 다르게 봤는지를 적는다.

```markdown
# 적중표 {pair} ({YYYY-MM-DD})
> 블라인드 판정 잠금: {lock.sha의 해시 앞 12자} · 결과 수집일: ...
## 한 줄 결론
## 포맷별 적중 (ledger.py hits 출력)
## 쌍 구분
## 무엇이 맞았고 왜 — 판정문의 어느 주장·기준이 결과와 맞았나
## 무엇이 틀렸고 왜 — 놓친 신호, 과대평가한 근거, 블라인드에서 볼 수 없던 정보
## 판단 기준 수정안 (4절 형식)
## 한계 — 사례 수, 오염 가능성, AI 학습 지식, 결과 정의의 자의성
```

## 3. 원작 역유입 측정 설계

확장(드라마 방영, 웹툰 공개, 공연 개막) 뒤 원작 열람·거래액이 얼마나 늘었는지 잰다.

- **기간을 미리 정한다.** 기준 기간과 비교 기간의 길이를 같게, 확장 시작일 기준으로 정한다(예: 공개 전 4주 vs 공개 후 4주).
- **배수만 쓰지 않는다.** 완결작은 기준 시점 수치가 낮아 배수가 커진다. 절대 증가량과 함께 쓰고, 비교 기간을 각주로 단다.
- **대조군을 둔다.** 같은 기간, 비슷한 장르·규모의 확장하지 않은 IP 변화와 비교한다.
- **플랫폼 밖 효과는 따로 본다.** 같은 플랫폼 안의 웹툰 → 원작 이동과, 공연·영상 같은 플랫폼 밖 포맷의 효과는 다르다.

## 4. 판단 기준 수정안

```markdown
| # | 바꿀 곳(스킬·절) | 지금 기준 | 제안 | 근거 사례(판정 id) | 근거 수 | 분류 |
```

- 두 사례 이상이 같은 방향을 가리킬 때만 `수정 제안`, 한 사례면 `관찰`로 분류한다.
- 특정 IP에만 맞는 규칙("○○ 장르는 무조건 B")을 쓰지 않는다. 여러 IP에 적용되는 원리로 쓴다.
- 스킬을 직접 고치지 않는다. 오케스트레이터가 사용자 승인을 받아 `harness:evolve`로 반영한다.

## 5. 출시 전 반응 테스트 설계(⑤)

피치 자료나 확장 계획을 출시 전에 작게 시험하는 설계서다. **성공 기준과 결정 규칙을 테스트 전에 정한다.** 결과를 본 뒤 기준을 정하면 어떤 결과든 성공으로 읽힌다.

```markdown
# {IP명} {포맷} 출시 전 반응 테스트 설계 ({YYYY-MM-DD})
| 가설 | 시험 방식 | 대상·규모 | 기간 | 측정 지표 | 성공 기준 | 결과별 결정(진행·수정·중단) |
## 시험 방식 후보 — 로그라인·키 비주얼 비교(사람 아트팀 제작물), 파일럿 회차 공개, 소규모 쇼케이스, 원작 독자 설문
## 원작 팬 위험 관리 — 스포일러, 휴재 중 노출, 권리 미확인 요소 사용 금지
## ⑦로 넘길 지표
```

## 6. 파일럿 측정 지표

`ledger.py report` 출력에 아래를 더해 보고한다.

| 지표 | 재는 방법 |
| --- | --- |
| 판단 준비 시간 | IP 하나의 판정서 초안까지 걸린 시간(워크플로 실행 시간). 사람 검토·판정 회의 시간은 따로 잰다 |
| 적중 | 사후 검증 쌍의 쌍 구분과 포맷별 적중 |
| 내부 지표의 차이 | 1차(공개 자료)와 2차(내부 지표 추가) 판정이 달라진 포맷 수 |
| 심사가 깎은 주장 | 조건부·기각으로 돌린 주장 수 |
| 초안과 결정의 차이 | AI 등급 초안과 사람 결정이 달라진 칸 수와 이유 |
| 원문과 다시 맞춘 숫자·사실 | 검증자가 refuted로 돌린 숫자·사실 건수 |
| 판정 회의 참여 | 의견을 낸 조직 수(오케스트레이터가 회의 기록에서 센다) |
