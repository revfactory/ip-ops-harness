# 판정서와 보고서

판정서의 독자는 판정 회의에 들어오는 사람들(CIPO, 스토리·미디어·공연·데이터 담당)이다. 이들은 판정문 원문을 다시 읽지 않는다. 그래서 판정서가 원문보다 밝게 읽히면 회의는 원문과 다른 판정을 결정하게 된다. 판정서의 일은 **결정할 것을 앞에 두고, 판정은 원문 그대로 옮기는 것**이다.

## 1. 옮기는 규칙

1. **원문 그대로 옮길 것**: 한 줄 판정, 포맷별 판정과 이유, 뒤집기 조건, 90일 권고, 하지 말 것. 요약하면 단서가 빠진다.
2. **단서를 지킨다**: 판정문의 "다만", "~전까지는", "미확인", "가정", "(부분 심사)"는 판정서에도 같은 자리에 둔다.
3. **결정 칸은 비운다**: AI가 결정 칸을 채우면 초안과 결정의 차이를 잴 수 없다.
4. **사람이 하지 않은 일을 사람이 했다고 쓰지 않는다**: 오케스트레이터는 메인 AI다. 사람이 검토하지 않았으면 한계에 그렇게 적는다.
5. **숫자 기준은 하나**: 같은 IP의 숫자는 판정문이 쓴 기준값을 쓴다. 이전 값은 추이로만 쓴다.
6. **새 분석을 하지 않는다**: 판정문과 분석 파일에 없는 숫자·권고를 만들지 않는다.

## 2. 판정서 형식

```markdown
# {IP명} 판정서 — {n}차({공개 자료 | 공개 자료 + 내부 지표}) · {YYYY-MM-DD}

> **AI 등급 초안: {등급}** — {한 줄 판정 그대로}
> 판정 회의용 준비 자료다. 아래 '결정' 칸은 회의에서 사람이 정한다.

## 1. 회의에서 정할 것
| # | 안건 | AI 초안 | 결정하는 사람(제안) | 결정 | 이유(초안과 다르면) |
| 1 | 전체 등급 | {등급} | CIPO | | |
| 2 | {포맷} 진행 여부 | {포맷 판정} | {사업부} | | |
| … | 뒤집기 조건 확인 담당·기한 | {조건} | {담당 후보} | | |

## 2. 포맷별 판정(판정문 그대로)
## 3. 판정을 뒤집을 확인 사항
| 방향 | 확인 사항 | 이렇게 나오면 | 바뀌는 판정 | 누가·언제 확인 |
## 4. 신호 요약
- 공개 신호 3줄(신호 카드) / 내부 신호 3줄(있을 때)
## 5. 확장 순서와 맡을 사업부(심사 후 순서)
## 6. 글로벌 첫 진출(판정문이 택한 쪽)
## 7. 권리 확인 질문(법무·사업)
## 8. 사업부별로 회의 전에 볼 것
| 사업부 | 볼 칸 | 회의에서 답해 줄 질문 |
## 9. 심사 기록
- 주장 {n}개 → 통과 {n} · 조건부 {n} · 기각 {n}, 검증자 제안을 바꾼 주장 {n}
- 기각된 주장 가운데 판정에 영향이 큰 것 3개와 이유
## 10. 1차 대비 바뀐 칸(2차 이상)
## 11. 이 판정의 한계
## 부록. 원본 파일
## 수정 기록
```

**사업부별로 볼 것**은 확장 지도의 담당 사업부를 기준으로 쓴다. 기본은 스토리(작품 PD), 미디어(영상 기획), 공연(쇼노트, 별도 법인), 플랫폼 데이터 담당이다. 뮤직·아티스트는 판정에 음악 포맷이 들어갈 때만 넣는다.

## 3. 판정 회의 뒤

오케스트레이터가 사용자에게서 결정을 전해 들으면 `ledger.py add-decision`으로 기록하고, 판정서의 결정 칸을 채운 사본을 `deliverables/`에 둔다. 작성자는 결정 내용을 추측해 채우지 않는다.

## 4. 파일럿 보고서(보고 모드)

착수·중간·최종 보고에 쓴다. 판정서 여러 부를 다시 쓰지 않고 묶는다.

```markdown
# IP 사업 운영 하네스 파일럿 {중간 | 최종} 보고 ({YYYY-MM-DD}, {n}주 차)
## 한 장 요약 — 판정서 {n}부, 적중표 {n}부, 결정할 것(계속·중단·확대)
## 1. IP별 판정 — | IP | 1차 | 2차 | 사람 결정 | 달라진 칸 |
## 2. 사후 검증 — 쌍 구분과 포맷별 적중(적중표 그대로), 오염 여부
## 3. 측정 지표 — ledger.py report 출력 + 판단 준비 시간 기준값 비교
## 4. 판단 기준 수정안 — 성과 분석가의 수정 제안·관찰
## 5. 안 된 것과 이유 — 데이터 추출 지연, 권리 미확인, 오염 등
## 6. 다음 단계 제안 — 기간·범위는 '(제안)'으로 표시
```

## 5. 검토

작성이 끝나면 dossier-reviewer가 `references/review-checklist.md`로 대조한다. 검토 의견의 높음·중간 항목만 고치고, 반영하지 않은 의견은 이유와 함께 `## 수정 기록`에 남긴다.
